## 写在前面

模型厂商的宣传页上，"128k 上下文""1M 超长上下文"的字样越来越常见。听起来像是：只要把整本书塞进去，模型就能全部记住、全部理解。

但真正用过的人会发现问题：

- 塞进去 10 万字，首 token 要等十几秒；
- 明明资料就在中间，模型却答"文中没有提到"；
- 开两个长对话，显卡显存就爆了；
- 同一个模型，8k 上下文很聪明，128k 上下文反而变笨。

这些现象指向大模型架构里两个绕不开的关键词：**上下文窗口（context window）** 和 **KV Cache**。

这一篇我们不讲虚的，直接从公式和真实数字出发，回答四个问题：

1. 上下文窗口到底是什么，为什么不能无限大？
2. 为什么长上下文又慢又贵？钱花在哪了？
3. KV Cache 是什么，一个 token 到底占多少显存？
4. "长上下文"和"真记住"是一回事吗？什么时候该用 RAG？

这是「大模型基础」系列的第五篇。前面我们讲了 token、GPT 结构、采样和训练；这一篇讲推理阶段最现实的约束：**显存和算力。**

## 一、上下文窗口：模型的工作台，不是硬盘

### 1.1 它到底是什么

上下文窗口指的是：**模型在一次请求中能处理的最大 token 数**，包括输入（prompt）和输出（completion）。

```
上下文窗口 = 输入 token + 输出 token ≤ 模型上限
```

比如 8k 窗口，你贴了 7000 token 的资料，那最多只能生成约 1000 token 的回答。很多 API 报错"context length exceeded"，就是这笔账超了。

### 1.2 它不是"记忆"

一个常见误解：以为上下文里的内容会被模型"记住"，下次对话还能用。

不是的。**大模型本身没有跨请求的状态。** 每次调用，你都要把完整的对话历史重新发给它；模型把整段文本重新编码一遍，算出回答，然后**全部忘掉**。下一次请求，它又是白纸一张。

所谓"多轮对话记忆"，是应用层把历史消息拼进 prompt 实现的：

```
第 1 轮： [系统提示][用户问题1][助手回答1]
第 2 轮： [系统提示][用户问题1][助手回答1][用户问题2][助手回答2]
第 3 轮： ...越来越长...
```

所以多轮聊久了，要么超上下文，要么得做"历史压缩/摘要"，要么用外部记忆库。**上下文是工作台，不是硬盘。**

### 1.3 为什么不能无限加长

两个硬约束：

1. **位置编码**：模型需要知道每个 token 在序列里的位置。训练时见过的最长序列是 4k，推理时突然给 100k，位置编码会进入"没训练过的区域"，效果断崖式下降；
2. **注意力复杂度**：标准注意力对序列长度是**平方级**的，长度翻倍，计算量翻四倍，显存也涨。

所以"支持 128k"不是改一个配置项就行，背后要做位置编码外推、长语料继续训练、注意力算子优化、显存管理等一系列工程。

## 二、注意力为什么是平方级

### 2.1 一笔账

Transformer 每一层都有自注意力。对长度为 `n` 的序列：

- 计算注意力分数矩阵 `Q·Kᵀ`：`n × n` 个分数；
- 每个分数要做 `d` 维点积：约 `n² · d` 次乘加；
- 对 `n` 个位置做 softmax 和加权求和：还是 `n² · d`。

一层就是 `O(n² · d)`，`L` 层就是 `O(L · n² · d)`。

| 序列长度 | 相对计算量（以 8k 为 1） |
|---|---|
| 8k | 1× |
| 32k | 16× |
| 128k | 256× |
| 1M | 16,384× |

注意，这是**每个 token 的生成过程**都要承担的（严格说是 prefill 阶段一次算完，decode 阶段每步对历史做注意力）。长度涨 16 倍，算力涨 256 倍，这就是长上下文昂贵的第一层原因。

### 2.2 Prefill 和 Decode：两种完全不同的阶段

大模型推理分两个阶段，理解它们才能理解"为什么首 token 慢、后面快"：

| 阶段 | 做什么 | 特点 | 瓶颈 |
|---|---|---|---|
| **Prefill（预填充）** | 把整段 prompt 一次性并行计算，建立 KV Cache | 计算密集、可并行 | GPU 算力 |
| **Decode（解码）** | 每次生成 1 个 token，读 KV Cache 做注意力 | 串行、每步只算一个 token | 显存带宽 |

所以：

- **首 token 延迟（TTFT）** 主要花在 prefill：prompt 越长，等得越久，而且是平方级增长；
- **每秒生成 token 数（TPOT）** 主要花在 decode：每步要把 KV Cache 从显存读一遍，上下文越长，读得越多，越慢。

一个 10 万 token 的 prompt，prefill 可能要几十秒；而生成阶段每多一个 token，都要和这 10 万个历史 token 做注意力。**长上下文的贵，是"读"和"算"双重叠加的贵。**

## 三、KV Cache：用显存换时间

### 3.1 没有 KV Cache 会怎样

自回归生成是逐 token 的：

```
第 1 步：输入 [A]                 -> 生成 B
第 2 步：输入 [A, B]              -> 生成 C
第 3 步：输入 [A, B, C]           -> 生成 D
```

如果没有缓存，第 3 步要把 A、B、C 重新过一遍所有层，算出它们的 K、V；第 4 步又要重算 A、B、C、D……**生成第 t 个 token 时，要把前 t 个 token 全部重算一遍**，累计计算量是 `O(n³)`，显存访问也成倍增加。这就是 KV Cache 存在的理由。

### 3.2 缓存的是什么

注意力里，每个 token 会产生三样东西：

- **Q（Query）**：我这次要"查什么"；
- **K（Key）**：我能"被怎么查"；
- **V（Value）**：我实际携带的信息。

生成新 token 时，只需要它的 Q，去和**所有历史 token 的 K、V** 做注意力。历史 token 的 K、V 不会变，于是可以缓存起来，每层、每个头都存一份：

```
第 1 层: K[1..t], V[1..t]
第 2 层: K[1..t], V[1..t]
...
第 L 层: K[1..t], V[1..t]
```

这样每生成一个 token，只需算它自己的 Q、K、V，然后读缓存做注意力。**计算量从"每步重算全部历史"降到"每步只算新 token"，代价是显存。**

一句话：**KV Cache 是用显存换时间。**

### 3.3 一个 token 占多少显存

公式很简单：

```
KV 字节数 = 2 × 层数 × KV 头数 × 每头维度 × 序列长度 × 批大小 × 每个元素的字节数
```

其中：

- `2` 是 K 和 V 两份；
- `KV 头数` 不是注意力头总数，而是 **Key/Value 的头数**（GQA 下比 Q 头少）；
- fp16 每个元素 2 字节，fp8 是 1 字节，int8 也是 1 字节。

以 **Llama-3-8B** 为例：32 层、8 个 KV 头（GQA）、每头 128 维、fp16：

```
2 × 32 × 8 × 128 × 2 = 131,072 字节 = 128 KiB / token
```

也就是说，**每多一个 token，显存多占 128 KiB**。换算一下：

| 上下文长度 | KV Cache（单请求） |
|---|---|
| 4k | 512 MiB |
| 8k | 1 GiB |
| 32k | 4 GiB |
| 128k | 16 GiB |

而模型权重（fp16）本身约 15 GiB。一张 24GB 显卡，装下权重后只剩 7~8 GiB 给 KV Cache 和激活值——**128k 上下文根本放不下一个请求**。

### 3.4 不同模型的差距有多大

| 模型 | 层数 | KV 头数 | 每 token | 8k | 128k |
|---|---|---|---|---|---|
| GPT-3 175B（MHA） | 96 | 96 | 4.5 MiB | 36 GiB | 576 GiB |
| Llama-3-8B（GQA） | 32 | 8 | 128 KiB | 1 GiB | 16 GiB |
| Llama-3-70B（GQA） | 80 | 8 | 320 KiB | 2.5 GiB | 40 GiB |
| Qwen2.5-7B（GQA） | 28 | 4 | 56 KiB | 448 MiB | 7 GiB |
| Qwen2.5-72B（GQA） | 80 | 8 | 320 KiB | 2.5 GiB | 40 GiB |

看第一行：GPT-3 用的是**多头注意力（MHA）**，每个头都有独立的 K、V，175B 模型每 token 要 4.5 MiB。8k 上下文就要 36 GiB，比很多显卡的总显存还大。这就是为什么后来的模型普遍改用 **GQA（分组查询注意力）**：

- **MHA**：每个 Q 头配一个 K/V 头，最贵；
- **MQA**：所有 Q 头共享一组 K/V，最省，但效果略降；
- **GQA**：把 Q 头分组，每组共享一组 K/V，效果和显存的折中。

Llama-3-8B 的 32 个注意力头只配了 8 组 K/V，KV Cache 直接降到 MHA 的 1/4。Qwen2.5-7B 更激进，28 个头只配 4 组，每 token 仅 56 KiB。

### 3.5 显存预算实战

以"24GB 显卡跑 Llama-3-8B"为例：

```
模型权重（fp16）:      约 15 GiB
预留激活/框架开销:      约 2 GiB
可用于 KV Cache:        约 7 GiB
每 token:              128 KiB
总 token 容量:          约 58,000 个 token（所有并发请求加起来）
```

这意味着：

- 单个请求 4k 上下文：理论上可并发约 14 路；
- 单个请求 8k：约 7 路；
- 单个请求 32k：只能 1 路，而且很紧张。

**并发和上下文长度是互相挤占的。** 你不可能既让 100 个用户各聊 32k，又只用一张 24GB 卡。生产环境要么加卡，要么做 KV 量化/分页/淘汰，要么限制上下文。

> 注：DeepSeek 系列用的 **MLA（多头潜在注意力）** 把 K/V 压缩成一个低维潜向量，KV Cache 比 GQA 还小一个量级。这是另一条技术路线，公式不同，但"用显存换时间"的本质一样。

## 四、位置编码：模型怎么知道"谁在前谁在后"

注意力本身是**无序**的：把句子打乱，`Q·Kᵀ` 的结果只是换了个顺序。所以必须额外注入位置信息。

### 4.1 三代位置编码

| 方式 | 做法 | 代表 | 局限 |
|---|---|---|---|
| **绝对位置嵌入** | 给每个位置学一个向量，加到 token 上 | GPT-2 | 超过训练长度就没见过，无法外推 |
| **正弦位置编码** | 用 sin/cos 函数生成固定位置向量 | 原始 Transformer | 相对关系隐式，外推一般 |
| **RoPE（旋转位置编码）** | 把 Q、K 按位置旋转一个角度，使点积只依赖相对距离 | LLaMA、Qwen、GPT-NeoX | 需要调 base 才能扩长度 |

RoPE 是现在的主流。它的巧妙之处在于：**两个 token 的 Q、K 点积，只和它们的相对位置差有关**，和绝对位置无关。这让模型天然具备"相对位置"的直觉，也为长度外推留下了操作空间。

### 4.2 为什么改个 `max_length` 不能变长

很多人以为把配置里的 `max_position_embeddings` 从 4096 改成 131072，模型就能吃 128k。不行。原因：

1. 模型训练时只见过 4k 内的位置组合，长距离的注意力模式**没学过**；
2. RoPE 的频率在超出训练范围后会"转得过头"，导致注意力分数分布偏移；
3. 直接外推，困惑度（perplexity）会爆炸，输出变成重复或胡话。

正确的做法是**继续训练 + 位置插值**：

- **Position Interpolation（PI）**：把 100k 的位置"压缩"到 4k 的范围内，相当于把长文本挤进模型熟悉的区间；
- **NTK-aware / YaRN**：调整 RoPE 的 base 频率，让不同维度以不同速度旋转，兼顾近处和远处；
- **继续预训练**：用长文本语料再训一段，让模型真正见过长距离依赖。

所以"支持 128k"的模型，通常在 4k/8k 预训练后，会用 32k、128k 的长语料做继续训练。**上下文长度是训练出来的，不是配置出来的。**

### 4.3 长上下文真的能用满吗

这是最容易被营销误导的地方。

**"能放进去"和"能用好"是两回事。** 研究（如 *Lost in the Middle*, Liu et al. 2023）发现，把关键信息放在长文档的**开头或结尾**，模型答得较好；放在**中间**，准确率明显下降，呈现"U 形曲线"。

原因不神秘：

- 注意力被大量无关 token 稀释，关键信息的权重被摊薄；
- 训练数据里"重要信息在中间"的样本相对少；
- 位置越远，相对位置信号越弱。

所以：

- 长上下文适合"整体理解、摘要、跨段落关联"；
- 精确查找某个细节，**RAG（检索增强）往往更稳、更便宜**；
- 把最关键的信息放在 prompt 的开头或结尾，比塞在中间有效。

## 五、让长上下文变得可行的技术

| 技术 | 解决什么 | 代价 |
|---|---|---|
| **FlashAttention** | 不显式存 `n×n` 注意力矩阵，分块计算，省显存、提速 | 仍是 `O(n²)` 计算 |
| **GQA / MQA** | 减少 KV 头数，直接缩小 KV Cache | 表达能力略降 |
| **滑动窗口注意力** | 每个 token 只看最近 W 个，KV 只存 W | 丢失超长距离信息 |
| **稀疏 / 环形注意力** | 只算部分注意力，或把序列切到多卡 | 实现复杂，效果依任务 |
| **PagedAttention（vLLM）** | KV 按页管理，减少显存碎片，提高并发 | 需要推理框架支持 |
| **Prefix Caching** | 相同前缀的 KV 复用，避免重复 prefill | 只对相同前缀有效 |
| **KV 量化（fp8/int8）** | KV 显存减半 | 可能轻微掉点 |
| **KV 淘汰 / 压缩** | 丢掉不重要的历史 token | 可能丢关键信息 |

几个常见误解：

- **FlashAttention 不减少 KV Cache**。它优化的是注意力计算过程中的中间矩阵，让长序列跑得动，但历史 token 的 K/V 还是要存；
- **滑动窗口不等于长上下文**。它让模型能跑很长，但每个 token 只看局部，跨章节的关联会丢；
- **1M 上下文不是"免费"的**。要么用 MoE 把激活参数量压下来，要么用更激进的注意力近似，成本仍然存在。

## 六、长上下文 vs RAG：怎么选

| 维度 | 长上下文 | RAG |
|---|---|---|
| 成本 | 每次请求都重新 prefill，贵 | 只检索相关片段，便宜 |
| 延迟 | 首 token 慢，随长度平方增长 | 检索快，prompt 短 |
| 新鲜度 | 依赖你贴进去的内容 | 知识库可实时更新 |
| 可追溯 | 模型不一定引用来源 | 可返回文档和出处 |
| 多跳推理 | 全文都在，适合跨段关联 | 检索不到就答不出 |
| 超长文档 | 受窗口和显存限制 | 可处理任意规模 |
| 隐私 | 全文进模型 | 只送相关片段 |

实践中的组合拳：

1. **先 RAG 召回**，把候选缩小到几千 token；
2. **再长上下文**做跨片段整合和推理；
3. 关键结论要求**引用原文**，方便人工核对；
4. 对高频、固定的长文档，用 **prefix caching** 摊销 prefill 成本。

一句话：**RAG 解决"找得到"，长上下文解决"看得全"，两者不是替代关系。**

## 七、动手：算一算你的显存够不够

下面这段代码可以直接跑，输入模型配置，算出每 token 的 KV Cache 和不同上下文下的占用：

```python
def kv_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
    # 2 = K 和 V 两份
    return 2 * layers * kv_heads * head_dim * dtype_bytes

def human(n):
    for unit in ['B', 'KiB', 'MiB', 'GiB', 'TiB']:
        if n < 1024:
            return f'{n:.1f} {unit}'
        n /= 1024
    return f'{n:.1f} TiB'

models = [
    ('Llama-3-8B',  32, 8, 128),
    ('Llama-3-70B', 80, 8, 128),
    ('Qwen2.5-7B',  28, 4, 128),
]

for name, layers, kv_heads, head_dim in models:
    per = kv_per_token(layers, kv_heads, head_dim)
    print(f'{name}: {human(per)}/token, '
          f'8k={human(per*8192)}, 32k={human(per*32768)}, 128k={human(per*131072)}')
```

真实输出：

```
Llama-3-8B: 128.0 KiB/token, 8k=1.0 GiB, 32k=4.0 GiB, 128k=16.0 GiB
Llama-3-70B: 320.0 KiB/token, 8k=2.5 GiB, 32k=10.0 GiB, 128k=40.0 GiB
Qwen2.5-7B: 56.0 KiB/token, 8k=448.0 MiB, 32k=1.8 GiB, 128k=7.0 GiB
```

再算并发：

```python
per = kv_per_token(32, 8, 128)          # Llama-3-8B
weights = 8e9 * 2                        # fp16 权重约 15 GiB
free = 24 * 1024**3 - weights - 2 * 1024**3
print(f'可用于 KV: {human(free)}，总共约 {int(free / per):,} token')
for ctx in [4096, 8192, 32768]:
    print(f'{ctx} token/请求 -> 约 {int(free / (per * ctx))} 路并发')
```

输出：

```
可用于 KV: 7.1 GiB，总共约 58,153 token
4096 token/请求 -> 约 14 路并发
8192 token/请求 -> 约 7 路并发
32768 token/请求 -> 约 1 路并发
```

把这套算法套到你自己的模型和显卡上，就能在部署前回答："我到底能开多长的上下文、扛多少并发？"而不是等 OOM 了再猜。

## 八、常见疑问

**Q1：为什么首 token 那么慢，后面反而快？**
首 token 要 prefill 整段 prompt，计算量和长度平方相关；后续 decode 每步只算一个新 token，主要受显存带宽限制。prompt 越长，这个差距越明显。

**Q2：KV Cache 能跨请求共享吗？**
只有**相同前缀**可以。vLLM 的 prefix caching、各家 API 的 prompt caching，都是把相同开头部分的 KV 存下来复用。所以系统提示、固定文档放在最前面，能省不少钱和时间。

**Q3：上下文越长，模型越聪明吗？**
不一定。信息太多会稀释注意力，中间位置尤其容易被忽略。把关键信息放开头/结尾、分块处理、配合检索，通常比"一股脑塞进去"效果好。

**Q4：KV Cache 量化会掉多少点？**
fp8 通常几乎无损，int8 可能有轻微下降，int4 就需要谨慎评估。具体取决于模型、任务和校准方法，别只看论文里的平均值。

**Q5：为什么 1M 上下文的模型，价格没有涨 1000 倍？**
厂商用了 MoE（每次只激活部分参数）、更高效的注意力、KV 压缩、批量调度等手段，把单位成本压下来了。但"总价"仍然随长度增长，而且长请求的并发能力会下降。

**Q6：本地部署，显存不够怎么办？**
优先级：换更小的模型 → 用 GQA 的模型 → KV 量化 → 限制上下文/并发 → 用 vLLM 等分页框架 → 加卡。不要一上来就上 4-bit 权重量化，那会影响所有请求的质量。

## 九、总结

把这一篇压缩成一条链：

```
上下文窗口 = 输入 + 输出 token 上限
  ├─ 位置编码限制（训练见过多长）
  └─ 注意力成本 O(n²)
        ├─ Prefill：首 token 慢，算力瓶颈
        └─ Decode：每步读 KV Cache，显存带宽瓶颈
              └─ KV Cache = 2 × 层数 × KV头数 × 头维度 × 长度 × 批大小 × 字节数
```

记住五句话：

1. **上下文是工作台，不是硬盘**；模型不会跨请求记住任何东西。
2. **长上下文的贵，来自平方级的注意力和线性增长的 KV Cache**。
3. **GQA/MQA 是在省 KV Cache**，FlashAttention 是在省注意力计算的中间显存，两者不是一回事。
4. **位置编码决定"能不能外推"**，长上下文必须靠继续训练，不是改配置。
5. **能放进去 ≠ 能用好**；关键信息放两头，精确查找用 RAG。

动手建议：

1. 用第七节的代码算一算你常用模型的 KV Cache，看看一张卡能扛多少并发；
2. 找一个长文档任务，把同一段关键信息分别放在开头、中间、结尾，对比模型表现；
3. 试试 vLLM 的 prefix caching，观察首 token 延迟的变化；
4. 读一读 *Lost in the Middle* 这篇论文，理解"长上下文"的能力边界。
