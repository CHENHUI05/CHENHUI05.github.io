## 写在前面

你给大模型 API 付的钱，是按 **token** 算的，不是按字数，也不是按单词数。

同样一段意思，写成英文可能只要 20 个 token，写成中文可能要 35 个；同一个问题问两遍，第二次如果多了几个空格，token 数也可能变化。更诡异的是，很多人发现模型数不清 `strawberry` 里有几个 `r`——因为在它眼里，`strawberry` 根本不是由字母组成的，而是一两个**整体编号**。

这些现象背后是同一个东西：**Tokenizer（分词器）**。

它是大模型流水线的第一道工序，也是最多人忽略的一道。模型再聪明，也只能处理分词器递给它的那串整数。这一篇我们就把它拆开：

- 为什么不能直接按"字"或按"词"切？
- BPE 算法到底在合并什么？用一百来行纯 Python 亲手实现；
- 字节级 BPE 如何做到"任何文字都能编码"；
- 词表大小如何影响参数量、上下文和账单；
- 实际开发中最容易踩的 token 坑。

这是「大模型基础」系列的第二篇。第一篇我们手撕了迷你 GPT，知道了模型在"预测下一个 token"；这一篇回答一个更前置的问题：**token 到底是什么？**

## 一、先看三个真实场景

### 1.1 场景一：同一个问题，中英文价格不同

假设你调用某家 API，价格是"每百万 token 若干元"。你写：

```
中文：请解释一下什么是机器学习。
英文：Please explain what machine learning is.
```

两句话意思一样，但分词后的 token 数通常不同。英文大约 8 个 token，中文常见分词器下大约 10~14 个。原因很简单：**分词器的词表是按训练语料的统计规律构建的，英文语料多，英文的常见词和词片段被合并得更充分，压缩率更高。**

这不是"中文更难"，而是分词器的"偏心"。它直接影响三件事：

1. **钱**：同样内容，token 多的语言更贵；
2. **速度**：token 多，生成同样内容需要的步数多；
3. **有效上下文**：128k token 的窗口，中文能装的内容比英文少。

### 1.2 场景二：为什么模型数不清字母

`strawberry` 被 GPT-2 的分词器切成 `straw` + `berry` 两个 token（不同版本可能略有差异）。模型看到的是两个编号，而不是 10 个字母。它当然可以靠训练中学到的拼写关联答对，但"逐字母操作"对它来说天生别扭。

同理，模型做多位数乘法容易出错，一个重要原因是数字被切得七零八落：

```
"123456" 可能被切成 ["123", "456"] 或 ["12", "345", "6"]
```

它看到的不是六个数位，而是几个"块"。所以现在的大模型遇到算术、字符串处理，普遍会调用计算器或代码解释器——不是它笨，是它的"眼睛"分辨率不对。

### 1.3 场景三：改一个空格，缓存失效

很多推理服务支持 **Prompt Caching（提示词缓存）**：前缀相同就能复用计算。但如果你在开头多打一个空格，或者把标点从全角改成半角，分词结果变了，缓存就命中不了，费用和延迟都会上升。

**Token 是模型世界的最小货币单位。** 不理解 token，就很难真正理解大模型的成本、速度和能力边界。

## 二、三种切法：字符、词、子词

要让模型处理文字，第一步是把一段字符串变成一串整数。切分粒度有三种选择。

### 2.1 按字符切（Character-level）

每个字符一个 token：

```
"我爱大模型" -> ["我", "爱", "大", "模", "型"] -> [7, 23, 105, 88, 66]
```

**优点**：词表极小（常用汉字几千个），永远不会遇到"没见过的词"，实现简单。

**缺点**：序列太长。一句话几百个字符，模型要处理的步数暴增；而且单个字符携带的语义太少，模型得花更多层才能把"大"和"模"拼成"大模"、再拼成"大模型"。

第一篇里我们的迷你 GPT 就是字符级的，因为玩具语料只有几百个字，字符级最省事。但真实大模型不会这么做。

### 2.2 按词切（Word-level）

每个词一个 token：

```
"我爱大模型" -> ["我", "爱", "大模型"] -> [7, 23, 1203]
```

**优点**：序列短，一个 token 就是一个完整语义单位。

**缺点**：词表会爆炸。中文词汇量以十万计，英文加上专有名词、缩写、变形更是无穷无尽。更致命的是 **OOV（Out-of-Vocabulary）问题**：训练时没见过的词（新人名、新梗、拼写错误、化学式）没有编号，只能统一变成 `<UNK>`，信息直接丢失。

### 2.3 按子词切（Subword-level）

这是现代大模型的答案：**常见词整块保留，罕见词拆成更小的片段。**

```
"我爱大模型"       -> ["我", "爱", "大模型"]
"我爱大语言模型"   -> ["我", "爱", "大", "语言", "模型"]
"unbelievable"    -> ["un", "believ", "able"]
```

这样既能控制词表大小（几万到二十万），又能表示任意新词：没见过的词总能拆成见过的片段。BPE、WordPiece、SentencePiece、Unigram 都属于这一类。

| 粒度 | 词表大小 | 序列长度 | 新词处理 | 典型代表 |
|---|---|---|---|---|
| 字符级 | 几千 | 很长 | 天然支持 | 早期 Char-RNN、玩具模型 |
| 词级 | 几十万+ | 短 | OOV 直接丢失 | 传统 NLP |
| 子词级 | 3 万 ~ 20 万 | 中等 | 拆成已知片段 | GPT、LLaMA、BERT、Qwen |

一句话总结：**子词分词是在"词表大小"和"序列长度"之间找平衡点的工程妥协。**

## 三、BPE：从字符开始，反复合并

BPE 全称 **Byte Pair Encoding（字节对编码）**，1994 年本来是一种数据压缩算法，2016 年被引入神经机器翻译，后来成了 GPT 系列的标配。

它的思想朴素到不可思议：

> 从最小的单位开始，反复把**最常一起出现的相邻两个 token** 合并成一个新 token。

就像整理衣柜：先按颜色分组，发现"黑色袜子"特别多，就把它们打包成一包；再发现"黑色袜子+黑色裤子"经常一起出现，再打成一个更大的包。合并的依据只有一个：**出现频率**。

### 3.1 一个经典的玩具例子

假设语料里只有四个词，出现次数如下：

```
low     出现 5 次
lower   出现 2 次
newest  出现 6 次
widest  出现 3 次
```

先给每个词末尾加一个特殊标记 `</w>`，表示"词到此结束"，这样 `low` 和 `lower` 里的 `low` 才能区分开：

```
l o w </w>          (5 次)
l o w e r </w>      (2 次)
n e w e s t </w>    (6 次)
w i d e s t </w>    (3 次)
```

统计所有相邻对：

| 相邻对 | 出现次数 |
|---|---|
| `l` + `o` | 5 + 2 = 7 |
| `o` + `w` | 5 + 2 = 7 |
| `e` + `s` | 6 + 3 = 9 |
| `s` + `t` | 6 + 3 = 9 |
| ... | ... |

出现最多的是 `e`+`s` 和 `s`+`t`（各 9 次）。选一个（比如 `e`+`s`）合并成新 token `es`，语料变成：

```
l o w </w>
l o w es r </w>
n e w es t </w>
w i d es t </w>
```

然后重新统计，继续合并。重复几轮之后，`est</w>`、`low</w>` 这些高频片段就诞生了，而 `widest` 会被切成 `wi` + `d` + `est</w>`——因为它整体不够常见，但词尾 `est` 很常见。

下面是真实运行结果（代码在第四节）：

```
第  1 次合并: 'e' + 's' (出现 9 次) -> 'es'
第  2 次合并: 'es' + 't' (出现 9 次) -> 'est'
第  3 次合并: 'est' + '</w>' (出现 9 次) -> 'est</w>'
第  4 次合并: 'l' + 'o' (出现 7 次) -> 'lo'
第  5 次合并: 'lo' + 'w' (出现 7 次) -> 'low'
第  6 次合并: 'n' + 'e' (出现 6 次) -> 'ne'
第  7 次合并: 'ne' + 'w' (出现 6 次) -> 'new'
第  8 次合并: 'new' + 'est</w>' (出现 6 次) -> 'newest</w>'
第  9 次合并: 'low' + '</w>' (出现 5 次) -> 'low</w>'
第 10 次合并: 'w' + 'i' (出现 3 次) -> 'wi'

合并后每个词被切成了：
  low     -> ['low</w>']
  lower   -> ['low', 'e', 'r', '</w>']
  newest  -> ['newest</w>']
  widest  -> ['wi', 'd', 'est</w>']
```

注意：这里的次数是**按词频加权**的——`e`+`s` 在 `newest`（6 次）和 `widest`（3 次）里都出现，所以权重是 9，而不是简单数"它在几个词里出现过"。代码里统计时会乘上词频。

结果很有意思：

- `low` 出现了 5 次，足够常见，被完整合并成一个 token；
- `newest` 出现 6 次，也被完整合并；
- `lower` 只出现 2 次，整体不够常见，最终被切成 `low` + `e` + `r` + `</w>`；
- `widest` 被切成 `wi` + `d` + `est</w>`，但词尾 `est</w>` 因为高频被保留了下来。

**这就是 BPE 的精髓：高频片段被保留，低频词被拆开。**

### 3.2 训练和编码是两个阶段

这一点初学者最容易混：

- **训练（training）**：在语料上统计、合并，产出一张**合并规则表**（以及最终词表）。这个过程只做一次，可能花几小时到几天。
- **编码（encoding）**：拿训练好的规则表，把新文本切成 token。这个过程必须很快，每次请求都要做。

编码时按**合并发生的先后顺序**依次尝试。先学的合并优先级高，因为它对应的片段更常见。这也是为什么同一个词在不同上下文里可能切法不同——分词器只认规则，不认语义。

## 四、手撕一个 BPE（纯 Python，一百来行）

下面这段代码不依赖任何第三方库，直接可跑。它包含 BPE 的全部核心：预切分、统计、合并、编码。

```python
def get_stats(ids, counts=None):
    """统计相邻 token 对的出现次数"""
    counts = {} if counts is None else counts
    for pair in zip(ids, ids[1:]):
        counts[pair] = counts.get(pair, 0) + 1
    return counts

def merge(ids, pair, idx):
    """把 ids 中所有 pair 替换成新编号 idx"""
    newids = []
    i = 0
    while i < len(ids):
        if i < len(ids) - 1 and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            newids.append(idx)
            i += 2
        else:
            newids.append(ids[i])
            i += 1
    return newids
```

训练循环。这里先做一个简单的**预切分**：用正则把连续的文字和标点分别切开，BPE 只在块内合并，避免出现"`。大模型`"这种跨标点的怪 token。（GPT-2 的正式实现也有一层正则预切分，规则更细。）

为了简单，这个正则把空格丢掉了；真实分词器会把空格也编码进 token（GPT-2 用 `Ġ` 表示前导空格），所以"空格也是 token"不是玩笑。

```python
import re

corpus = "大模型是人工智能领域的重要成果。大模型可以理解语言、生成文本、回答问题。..."
chunks = re.findall(r"\w+|[^\w\s]", corpus)  # 标点单独成块

chars = sorted(set(corpus))                 # 初始词表：所有出现过的字符
stoi = {c: i for i, c in enumerate(chars)}
itos = {i: c for c, i in stoi.items()}

chunk_ids = [[stoi[c] for c in chunk] for chunk in chunks]  # 每块一个 id 序列
merges = {}

for i in range(40):                         # 做 40 次合并
    stats = {}
    for ids in chunk_ids:
        get_stats(ids, stats)               # 统计所有块里的相邻对
    pair = max(stats, key=stats.get)        # 选出现最多的相邻对
    if stats[pair] < 2:
        break                               # 没有重复片段了，停
    new_id = len(itos)
    itos[new_id] = itos[pair[0]] + itos[pair[1]]
    chunk_ids = [merge(ids, pair, new_id) for ids in chunk_ids]
    merges[pair] = new_id
```

编码时也要做同样的预切分：

```python
def encode(text):
    ids = []
    for chunk in re.findall(r"\w+|[^\w\s]", text):
        part = [stoi[c] for c in chunk]
        while len(part) >= 2:
            stats = get_stats(part)
            # 在统计到的相邻对里，找"最早被合并"的那一个
            pair = min(stats, key=lambda p: merges.get(p, float("inf")))
            if pair not in merges:
                break
            part = merge(part, pair, merges[pair])
        ids.extend(part)
    return ids
```

在一段 157 字的中文语料上跑，真实输出是：

```
语料: 157 个字符 -> 31 个预切分块，初始 token 数: 156，字符词表: 86
  合并 # 1: '模' + '型' -> '模型'
  合并 # 2: '大' + '模型' -> '大模型'
  合并 # 3: '理' + '解' -> '理解'
  合并 # 4: '语' + '言' -> '语言'
  合并 # 5: '我' + '们' -> '我们'
  合并 # 6: '大模型' + '的' -> '大模型的'
  合并 # 7: '数' + '据' -> '数据'
  合并 # 8: '计' + '算' -> '计算'
  合并 # 9: '文' + '字' -> '文字'
合并 9 次后：token 数 126，平均 1.25 字符/token

大模型可以理解语言。  (10 字) -> 6 个 token: ['大模型', '可', '以', '理解', '语言', '。']
人工智能  (4 字) -> 4 个 token: ['人', '工', '智', '能']
```

只有 9 次合并，是因为语料太小，大部分相邻对只出现一次，不满足"至少出现 2 次"的条件。**真实分词器会在几十 GB 到几 TB 的语料上做几万到几十万次合并**，所以能学出 `ation`、`ization`、`大模型`、`人工智能` 这种长片段。

这段代码还有一个隐藏问题：`stoi` 只包含语料里出现过的字符。如果来一个没见过的字（比如语料里没有"春"），编码会直接报 `KeyError`。这正说明了字符级词表的死穴——**世界上的字符是开放的，而词表是封闭的**。解决方案就是下一节的字节级 BPE。

## 五、字节级 BPE：让词表覆盖"一切"

GPT-2 的天才之处，是把 BPE 的基本单位从"字符"换成了"字节"。

任何文本（中文、日文、阿拉伯文、emoji、二进制乱码）都可以用 UTF-8 编码成字节序列，而字节只有 0~255 共 256 种。于是：

1. 初始词表固定为 256 个字节，**永远不会 OOV**；
2. 在这个基础上做 BPE 合并，学出常见字节组合；
3. 一个汉字在 UTF-8 里通常占 3 个字节，如果它很常见，会被合并成一个或几个 token；如果很生僻，就保留成 2~3 个字节 token。

```
"大" 的 UTF-8 字节: E5 A4 A7   -> 初始 3 个 token
常见之后可能被合并: [E5A4A7] -> 1 个 token
"𠮷"（生僻字）: 4 个字节 -> 可能拆成 2~4 个 token
```

这就是为什么 GPT 系列"什么都能读"，连乱码和表情符号都不会报错。代价是：**分词结果不再直观**，一个 token 可能只是半个汉字（字节不完整），所以你不能简单地用字符串长度去估算 token 数。

GPT-2 的词表大小是 50257，GPT-4 用的 `cl100k_base` 约 10 万，GPT-4o 的 `o200k_base` 约 20 万，LLaMA 1/2 约 3.2 万，LLaMA 3 约 12.8 万，Qwen 系列约 15 万。词表越大，同样文本的 token 数越少，但嵌入矩阵也越大。

### 5.1 词表大小是一笔账

Transformer 里，token 嵌入矩阵的形状是 `词表大小 × 隐藏维度`。假设 `d_model = 4096`：

| 词表大小 | 嵌入参数量 | 说明 |
|---|---|---|
| 32,000 | 1.31 亿 | LLaMA 级别，省参数 |
| 100,000 | 4.10 亿 | GPT-4 级别 |
| 200,000 | 8.19 亿 | 多语言友好，但参数翻倍 |

而且输出层通常和嵌入层**共享权重**（weight tying），所以这个矩阵只存一份。但即便如此，词表从 3 万涨到 20 万，也要多出近 7 亿参数——对 7B 模型来说不是小数目。

另一个隐性成本是** softmax 的计算量**：每生成一个 token，都要在词表维度上做一次 softmax。词表越大，这一步越慢。所以词表大小是"压缩率"和"计算成本"之间的权衡。

### 5.2 为什么中文更"费 token"

现代分词器的训练语料以英文为主，英文的高频片段（`the`、`ing`、`tion`、`http`）被充分合并，一个 token 能装下好几个字母。中文的合并次数相对少，很多汉字只能以 1~2 个 token 表示。

一个粗略的经验值（不同分词器差异很大）：

| 内容 | 大约 token 数 |
|---|---|
| 1000 个英文单词 | 1300 ~ 1500 |
| 1000 个汉字 | 1000 ~ 2000 |
| 1000 个数字 | 300 ~ 1000（取决于切分策略） |
| 1000 个 emoji | 1000 ~ 3000 |

所以"上下文窗口 128k"不等于"能放 128k 个汉字"。用之前先估一下，别等报错才发现超了。

## 六、主流分词器家族

BPE 不是唯一选择，但它是目前最主流的。几张表帮你认路。

| 分词器 | 基本单位 | 词表 | 代表模型 | 特点 |
|---|---|---|---|---|
| **BPE** | 字节/字符 | 3 万 ~ 20 万 | GPT 系列、LLaMA、Qwen | 高频片段优先，工程成熟 |
| **WordPiece** | 字符 | 3 万左右 | BERT | 用似然而非频次选择合并，`##` 表示词中片段 |
| **SentencePiece** | 字符/字节 | 3 万 ~ 25 万 | T5、ALBERT、LLaMA | 把空格也当普通字符，语言无关 |
| **Unigram** | 子词 | 3 万 ~ 25 万 | SentencePiece 的一种模式 | 从大词表开始剪枝，概率建模 |

几个容易混淆的点：

- **BPE 和 WordPiece 都是子词算法**，区别在"合并谁"：BPE 选频次最高的对，WordPiece 选能让语料似然提升最大的对；
- **SentencePiece 不是算法，是工具**，它实现了 BPE 和 Unigram 两种模式，特点是"不依赖预分词"，直接把空格当字符处理，所以对中文、日文友好；
- **LLaMA 用的是 SentencePiece 的 BPE 模式**，不是纯 GPT-2 字节级 BPE，但思想一脉相承。

## 七、特殊 token 与对话模板

除了普通文字，分词器还要处理一些"控制信号"，它们叫**特殊 token（special tokens）**：

| 特殊 token | 作用 |
|---|---|
| `<BOS>` / `<s>` | 序列开始 |
| `<EOS>` / `</s>` | 序列结束，模型生成到它就停 |
| `<PAD>` | 批量推理时把短序列补齐 |
| `<UNK>` | 未知词（子词分词器一般不需要） |
| `<|im_start|>` / `<|im_end|>` | 对话角色边界（ChatML 格式） |
| `<|endoftext|>` | 文档分隔 |

现代聊天模型不是把"用户：你好\n助手："直接当普通文本，而是有一套**对话模板（chat template）**：

```
<|im_start|>system
你是一个乐于助人的助手。<|im_end|>
<|im_start|>user
什么是 BPE？<|im_end|>
<|im_start|>assistant
```

这些标记也是 token，也占上下文，也会计费。更关键的是：**模板必须和模型训练时一致**。用错了模板（比如该加 `<|im_start|>` 却没加），模型可能答非所问——它没见过这种格式。

Hugging Face 的 `tokenizer.apply_chat_template()` 就是干这个的。自己拼字符串很容易漏掉空格、换行、结束符，能用官方模板就别手写。

### 7.1 训练时的 loss mask

做 SFT（监督微调）时，一条样本通常是"问题 + 回答"。我们只希望模型学习**回答部分**，不希望它学习复述问题。做法是把问题部分的标签设成 `-100`，交叉熵会忽略这些位置：

```python
labels = input_ids.clone()
labels[:len(prompt_ids)] = -100   # 只对回答部分计算 loss
loss = F.cross_entropy(logits.view(-1, vocab_size), labels.view(-1), ignore_index=-100)
```

这也是为什么"token 数"和"训练 token 数"要分清：计费按全部 token，但 loss 可能只算一部分。

## 八、工程实践：六个 token 坑

### 坑 1：用 `len(text)` 估算 token 数

绝对不要。中文、英文、代码、emoji 的压缩率完全不同。正确做法是用对应模型的 tokenizer 实际编码：

```python
# Hugging Face
ids = tokenizer.encode(text)

# OpenAI
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")
ids = enc.encode(text)
```

如果只是粗略估算，可以按"中文 1 字 ≈ 1.5 token、英文 1 词 ≈ 1.3 token"心算，但别拿它做预算。

### 坑 2：以为 token 边界等于语义边界

`大模型` 可能是一个 token，也可能是 `大` + `模型`，取决于上下文和分词器版本。模型看到的序列不同，行为可能有细微差异。这也是为什么"改一个标点，输出就变了"。

### 坑 3：混用不同模型的 tokenizer

每个模型的词表不同，token id 不能跨模型通用。把 LLaMA 的 token id 喂给 Qwen，得到的是乱码。保存训练数据时，要么存原始文本，要么存对应模型的 tokenizer 版本号。

### 坑 4：忽略特殊 token 的计费

系统提示、对话模板、工具调用格式、图片占位符，全都是 token。一个复杂 Agent 的系统提示可能就有几千 token，每轮对话都要重复计费。**能缓存就缓存，能精简就精简。**

### 坑 5：中文标点与全半角

`，` 和 `,`、`。` 和 `.` 是完全不同的 token。用户输入里混用全半角，可能导致检索、匹配、缓存全部失效。做数据处理时先统一。

### 坑 6：以为换分词器不用重训

分词器一变，token id 全变，嵌入矩阵对不上，模型必须从头训练（或至少重新初始化嵌入层并继续预训练）。所以分词器一旦定下，通常整个模型生命周期都不换。

## 九、常见疑问

**Q1：BPE 合并多少次才够？**
没有标准答案。合并次数决定词表大小，词表大小要和模型规模、语料规模匹配。经验上，几十 GB 语料配 3 万~5 万词表，多语言大模型用 10 万~25 万。合并太多会导致词表里塞满长尾片段，浪费参数；太少则序列过长。

**Q2：为什么不用"最常用的 10 万个词"直接做词表？**
因为词的形态是开放的。中文有新词，英文有屈折变化，代码有任意标识符。固定词表必然遇到 OOV，而子词分词可以把任何新词拆成已知片段。

**Q3：一个 token 到底对应多少字？**
没有固定答案。英文大约 4 个字符，中文大约 1~2 个字符，代码和数字更碎。唯一可靠的办法是用目标模型的 tokenizer 实测。

**Q4：分词器会影响模型智商吗？**
会，而且影响不小。同样的内容，token 数越少，模型在固定上下文里能"看到"的信息越多，注意力也越集中；token 切得太碎，模型要花更多层去拼装语义。这就是为什么多语言模型要专门扩词表、做词表平衡。

**Q5：我自己微调，需要改分词器吗？**
一般不需要。除非你要加一种模型完全没见过的语言、大量领域专有符号（比如某种化学式），才考虑扩词表。扩词表后要重新初始化新 token 的嵌入，并用大量语料继续训练，否则新 token 等于噪声。

## 十、总结

把这一篇压缩成一张图：

```
原始文本
  → 预切分（按文字/标点切开）
  → 字节编码（UTF-8，256 个基础字节）
  → BPE 合并（按学到的规则，反复合并高频对）
  → token id 序列
  → 模型
```

记住四句话：

1. **大模型不认字，只认 token**；token 是它世界的原子。
2. **BPE 的本质是"高频合并、低频拆分"**，用一个可控大小的词表覆盖开放世界。
3. **字节级 BPE 保证永不 OOV**，代价是 token 边界不直观。
4. **token 数决定成本、速度和上下文**，别用字符数拍脑袋。

动手建议：

1. 把第四节的代码跑一遍，改改语料和合并次数，观察词表和切分结果怎么变；
2. 用你常用模型的 tokenizer，把同一段中文、英文、代码各编码一次，对比 token 数；
3. 找一段带 emoji 和生僻字的文本，看看字节级分词器怎么处理；
4. 打印一条真实对话的 `apply_chat_template` 结果，看看特殊 token 长什么样。

下一篇我们聊**采样**：模型输出的是整个词表上的概率分布，为什么同一个问题每次回答都不一样？温度、Top-k、Top-p 到底在调什么？我们会用一个纯 Python 的小实验，把"保守"和"发疯"调到肉眼可见。
