## 写在前面

你有没有遇到过这种情况：

- 同一个问题问两遍，一次答得中规中矩，一次脑洞大开；
- 把 `temperature` 从 0.7 调到 1.2，模型突然开始胡言乱语；
- 明明设了 `temperature=0`，两次调用结果还是有细微差别；
- 写代码时希望它稳定，写文案时希望它活泼，却不知道参数该怎么配。

这些都不是玄学，而是**解码策略（decoding strategy）**在起作用。

大模型每生成一个 token，输出的不是一个确定的词，而是**整个词表上的一个概率分布**。从"分布"到"最终选哪个词"，中间那一步就是采样。温度、Top-k、Top-p 都是在对这个分布做手术。

这一篇我们把手术刀拆开：

- logits 和 softmax 到底算出了什么；
- 贪心、温度、Top-k、Top-p 分别在改什么；
- 用真实数字看温度如何把分布"压尖"或"摊平"；
- 用一段纯 Python 代码写一个二元语言模型，亲眼看到"保守"和"发疯"的差别；
- 不同任务到底该怎么配参数。

这是「大模型基础」系列的第三篇。前两篇分别手撕了迷你 GPT 和 Tokenizer，这一篇接着讲：**模型吐出概率之后，发生了什么。**

## 一、模型输出的不是字，是分布

### 1.1 从 logits 到概率

假设词表里只有 6 个候选词，模型在某一步给出的 **logits**（未归一化的打分）是：

```
好: 3.0   很: 2.0   不: 1.5   太: 0.5   棒: 0.0   差: -0.5
```

logits 可以是任意实数，不是概率，加起来也不等于 1。要变成概率，过一遍 **softmax**：

```
p_i = exp(z_i) / Σ_j exp(z_j)
```

算出来是：

```
好: 0.570   很: 0.210   不: 0.127   太: 0.047   棒: 0.028   差: 0.017
```

意思是：模型认为下一个词是"好"的概率约 57%，"很"约 21%，以此类推。**注意，模型给出的是"可能性"，不是"决定"。** 最终选哪个，取决于解码策略。

### 1.2 为什么同一个问题每次答案不同

因为绝大多数对话模型默认**随机采样**：按概率抽签，抽到"好"就输出"好"，抽到"很"就输出"很"。

第一次抽到"好"，后面的话就往"好"的方向走；第二次抽到"很"，整句话的走向就变了。语言是链式反应，前面一个词不同，后面可能完全不同——这就是"同一个问题，两次回答不一样"的根源。

如果每次都选概率最高的词（贪心），输出就固定了，但会变得机械、重复。**随机性不是 bug，而是让模型"有创造力"的来源；关键是怎么控制它。**

## 二、贪心解码：永远选第一名

最简单的方式：每步都选概率最高的 token。

```
下一个词 = argmax(p)
```

优点是稳定、可复现、适合有标准答案的任务（分类、抽取、代码补全）。缺点是：

1. **容易重复**：一旦进入"的的的的"或"我认为我认为"的循环，就很难出来；
2. **容易平庸**：每一步都选最安全的词，整体可能寡淡；
3. **不等于全局最优**：贪心是局部最优，每一步都选最好的，合起来不一定是最好的句子。

用一个二元模型（只看前一个字预测下一个字）做实验，贪心生成的结果是：

```
春眠不觉晓，疑是地上霜。
```

前半句来自《春晓》，后半句却跳到了《静夜思》。每一步都选了最高概率，但连起来语义已经断裂。真实大模型比二元模型强得多，但"局部最优不等于全局最优"的道理是一样的。

## 三、温度：把分布压尖或摊平

### 3.1 公式

温度（Temperature，`T`）是加在 softmax 里的一个除数：

```
p_i = exp(z_i / T) / Σ_j exp(z_j / T)
```

- `T = 1`：原始分布；
- `T < 1`：logits 被放大，概率差距拉大，分布变**尖**，模型更保守；
- `T > 1`：logits 被缩小，概率差距变小，分布变**平**，模型更随机；
- `T → 0`：等价于贪心，只选概率最高的那个。

### 3.2 真实数字

还是上面那组 logits，换不同温度：

| 温度 | 好 | 很 | 不 | 太 | 棒 | 差 |
|---|---|---|---|---|---|---|
| T=0.3 | 0.959 | 0.034 | 0.006 | 0.000 | 0.000 | 0.000 |
| T=1.0 | 0.570 | 0.210 | 0.127 | 0.047 | 0.028 | 0.017 |
| T=2.0 | 0.362 | 0.220 | 0.171 | 0.104 | 0.081 | 0.063 |

看得很清楚：

- `T=0.3` 时，"好"占了 95.9%，几乎等于每次都选它，输出高度确定；
- `T=1.0` 时，前三个词还有竞争；
- `T=2.0` 时，六个词的概率被拉得很接近，连"差"都有 6.3% 的机会，模型开始"语无伦次"。

**温度不改变模型的知识，只改变它"冒险"的程度。** 它不知道的答案，调温度也变不出来；它知道的答案，温度太低会反复说同一句，温度太高会说出似是而非的变体。

### 3.3 温度不是越高越聪明

一个常见误解：温度高 = 创造力强 = 更聪明。不是的。

- 温度高只是**增加随机性**，随机不等于有创意。它可能把"月亮"换成"月壳"，把"因为"换成"因伪"；
- 温度低也不等于准确。贪心可能卡在重复循环里，反而更差。

创造力来自模型学到的组合能力，温度只负责"要不要冒险尝试低概率的分支"。写诗可以调到 0.9~1.1，写代码最好 0~0.2。

## 四、Top-k：只在前 k 名里抽

温度调整的是整个分布的形状，但长尾里那些概率极低的词依然可能被抽到。**Top-k** 的做法简单粗暴：

> 只保留概率最高的 k 个 token，其余全部丢掉，再把剩下的概率重新归一化。

```
候选 = 概率前 k 名
p'_i = p_i / Σ_{j∈候选} p_j
```

比如上面的分布，`top-k=3` 之后：

```
好: 0.629   很: 0.231   不: 0.140   其余: 0
```

这样无论温度多高，都不可能抽到"差"这种离谱的词。k 通常取 20~50，太小会限制表达，太大会让长尾重新混进来。

**Top-k 的问题在于 k 是固定的**：有的位置模型很确定（前 1 名 99%），有的位置模型很犹豫（前 10 名各占 10%）。固定 k 无法适应这种变化——确定的时候保留 50 个纯属浪费，犹豫的时候只留 50 个可能砍掉好选项。

## 五、Top-p：按累积概率动态截断

**Top-p**（也叫 nucleus sampling，核采样）解决了这个问题：

> 从高到低累加概率，凑够 p 就停，只保留这一小撮 token。

比如 `p=0.9`：

```
好 0.570  -> 累计 0.570
很 0.210  -> 累计 0.780
不 0.127  -> 累计 0.907  >= 0.9，停
```

候选就是前三个，和 `top-k=3` 结果一样。但如果模型很确定（"好"占 0.95），top-p 只保留 1 个；如果模型很犹豫（前 20 个各占 0.05），top-p 会自动保留 20 个左右。

**Top-p 的候选数量是动态的，跟着模型的置信度走**，这比固定 k 更合理，所以现在大多数 API 推荐"调 top-p，而不是 top-k"。

常见取值：`top-p = 0.9 ~ 0.95`。设成 1.0 等于不截断，长尾全部保留；设成 0.5 会非常保守。

### 5.1 Top-k 和 Top-p 一起用？

可以，但通常没必要。两者叠加时，先 top-k 再 top-p（或反过来），候选集是两者的交集，容易过度限制。多数场景选一个调就行：

- 想要"绝对不出现离谱词"：top-k；
- 想要"根据置信度自适应"：top-p；
- 两个都设：先 top-k 保底，再 top-p 截断，效果取更严格的那个。

### 5.2 新一点的选择：Min-p

Min-p 的思路是"相对阈值"：只保留概率不低于 `min_p × 最大概率` 的 token。

```
候选 = { i | p_i >= min_p * max(p) }
```

比如 `min_p=0.05`、最大概率 0.6，则阈值是 0.03，所有概率 ≥ 3% 的词都保留。它同样能随置信度自适应，而且在高温下比 top-p 更稳。一些开源推理框架已经支持，API 里还不算常见，遇到时可以试试。

## 六、重复惩罚：别让模型复读

即使有温度，模型也可能陷入循环：

```
我认为这个问题很重要，我认为这个问题很重要，我认为这个问题很重要……
```

**重复惩罚（repetition penalty）** 在采样前修改 logits：

```
如果 token 已经出现过：logit = logit / penalty   （penalty > 1 时降低）
```

`penalty` 通常取 1.0~1.3。设得太大，模型会刻意避开所有重复词，导致语句不通顺，甚至把"的"这种必需的功能词也压掉。

另外两种惩罚：

| 参数 | 作用 | 典型值 |
|---|---|---|
| `frequency_penalty` | 按出现次数线性扣分，越重复越压 | 0 ~ 1 |
| `presence_penalty` | 出现过就扣一次分，鼓励聊新话题 | 0 ~ 1 |

它们和 repetition penalty 的区别是：前者按"次数/是否出现"扣分，后者按"比例"压 logit。做长文生成时，适度加一点 frequency penalty 能明显减少车轱辘话。

## 七、其他解码方式

### 7.1 Beam Search（束搜索）

保留 top-b 条候选路径，每一步扩展、打分、剪枝，最后选总分最高的一条。它适合**翻译、摘要**这种"输入输出比较确定"的任务，但不适合开放对话——beam search 倾向于生成安全、常见、无聊的句子。

### 7.2 约束解码（Constrained Decoding）

如果你要模型输出 JSON，最可靠的办法不是"求它别写错"，而是**在解码时禁止非法 token**：用 JSON Schema 或语法自动机，把不符合语法的 token 概率置零。这叫 grammar-constrained decoding，vLLM、Outlines、llama.cpp 都支持。

它能把"JSON 解析失败率"从百分之几降到接近零，是大模型落地工程里非常实用的一招。

### 7.3 Logit Bias 与 Stop Sequences

- **logit bias**：给指定 token 加/减固定分数，比如禁止出现某些词、强制以某个词开头；
- **stop sequences**：生成到指定字符串就停，避免模型继续啰嗦；
- **seed**：部分 API 支持固定随机种子，提高可复现性（但不保证跨版本、跨硬件完全一致）。

### 7.4 投机解码（Speculative Decoding）

这不是改变"选什么词"，而是改变"算得多快"：用一个小模型快速草拟几个 token，大模型并行验证，接受就跳过。输出分布和大模型单独采样**理论上一致**，速度能提升 2~3 倍。它属于推理加速，不影响生成质量。

## 八、动手：一段代码看采样效果

下面这个实验不依赖任何库。先用一个二元模型（只看前一个字）在几首唐诗上统计转移概率，再用不同的温度/Top-k/Top-p 生成，直观感受差别。

```python
import math, random
random.seed(7)

def softmax(logits, T=1.0):
    z = [x / T for x in logits]
    m = max(z)
    e = [math.exp(x - m) for x in z]
    s = sum(e)
    return [x / s for x in e]

def top_k_filter(probs, k):
    order = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)[:k]
    out = [0.0] * len(probs)
    for i in order:
        out[i] = probs[i]
    return [p / sum(out) for p in out]

def top_p_filter(probs, p):
    order = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)
    out = [0.0] * len(probs)
    cum = 0.0
    for i in order:
        out[i] = probs[i]
        cum += probs[i]
        if cum >= p:
            break
    return [x / sum(out) for x in out]

def sample(probs):
    r, cum = random.random(), 0.0
    for i, p in enumerate(probs):
        cum += p
        if r < cum:
            return i
    return len(probs) - 1
```

统计转移表并生成：

```python
corpus = "床前明月光，疑是地上霜。举头望明月，低头思故乡。春眠不觉晓，处处闻啼鸟。……"
next_counts = {}
for a, b in zip(corpus, corpus[1:]):
    next_counts.setdefault(a, {})
    next_counts[a][b] = next_counts[a].get(b, 0) + 1

def generate(start, length=40, T=1.0, k=None, p=None, greedy=False):
    out, prev = [start], start
    for _ in range(length - 1):
        items = next_counts.get(prev)
        if not items:
            break
        chars = list(items.keys())
        probs = softmax([math.log(n / sum(items.values())) for n in items.values()], T)
        if k: probs = top_k_filter(probs, k)
        if p: probs = top_p_filter(probs, p)
        idx = max(range(len(probs)), key=lambda i: probs[i]) if greedy else sample(probs)
        out.append(chars[idx])
        prev = chars[idx]
    return "".join(out)
```

真实运行结果（摘录，每次运行会不同）：

```
贪心：
  春眠不觉晓，疑是地上霜。
T=0.3：
  春眠不见人，更上一层楼。红豆生南国，独钓寒江雪。
T=1.0：
  春来风雨声，花落知盘中，粒粒皆辛苦。欲穷千山鸟飞绝，此山中，但闻人，粒皆辛苦。
T=1.5：
  春眠不觉晓，言师采撷，低头思。返景入海流。谁知多少。夜来风雨声，独钓寒江雪。举头
T=1.0, top-k=5：
  春来发几枝。千里目，疑是地上霜。春来发几枝。春来发几枝。
```

观察几个现象：

1. **贪心**直接走进了"春眠不觉晓 → 疑是地上霜"的混合，而且因为语料里有换行，它开始循环复读；
2. **T=0.3** 还算通顺，但句子之间跳跃，像在拼贴；
3. **T=1.5** 已经完全放飞，"言师采撷""返景入海流"语法崩了；
4. **top-k=5** 虽然温度正常，但因为候选被压得太窄，反而更容易复读"春来发几枝"。

这个二元模型当然不能代表大模型，但**分布、采样、截断的机制是一模一样的**。你在大模型 API 上看到的所有"性格差异"，底层都是这套操作。

## 九、参数怎么配：一张实用表

| 任务 | temperature | top_p | 说明 |
|---|---|---|---|
| 代码生成 / SQL | 0 ~ 0.2 | 0.95 | 要稳定、可复现 |
| 数据抽取 / 分类 | 0 | 1.0 | 贪心最稳 |
| 翻译 / 摘要 | 0.3 ~ 0.5 | 0.9 | 少量多样性，避免死板 |
| 客服问答 / RAG | 0.1 ~ 0.3 | 0.9 | 忠于资料，别发挥 |
| 通用聊天 | 0.7 | 0.9 | 平衡 |
| 文案 / 起名 / 头脑风暴 | 0.9 ~ 1.1 | 0.95 | 鼓励发散 |
| 写诗 / 小说 | 1.0 ~ 1.2 | 0.95 | 可以更野一点 |
| 数学 / 推理 | 0 ~ 0.3 | 0.95 | 降低随机性，配合多采样投票 |

几条经验：

- **先调 temperature，再调 top_p**。温度是主旋钮，top-p 是保险丝；
- **不要同时把两个都调高**。`T=1.5 + top_p=1.0` 是"发疯套餐"；
- **代码/JSON 任务优先用约束解码**，比调温度靠谱；
- **需要多样性时，采样多次再选**（self-consistency），比一次高温生成更可控；
- **API 默认值通常就是 0.7 / 0.9 左右**，不知道用什么时先用默认。

## 十、常见误区

**Q1：`temperature=0` 就一定完全确定吗？**
不保证。GPU 浮点运算的顺序、批处理中其他请求的影响、不同推理框架的实现，都可能带来微小差异。工程上把它当"近似确定"，别当"绝对可复现"。真要可复现，固定 seed、固定 batch、固定硬件和框架版本。

**Q2：温度高是不是模型更聪明？**
不是。温度只改变采样随机性，不增加知识。高温会让模型更"敢说"，但不代表说得对。很多"高温更有创意"的体感，其实只是低概率词带来的新鲜感。

**Q3：为什么我设了 top_p=0.9，还是会出现奇怪的词？**
top-p 只截断概率质量，不判断语义。如果模型本身对某个错误答案给了 0.4 的概率，它依然会被抽到。**采样策略解决不了知识错误**，那是 RAG、工具调用和训练的问题。

**Q4：温度和 top-k/top-p 会改变模型"知道什么"吗？**
不会。它们只改变"从已知分布里怎么选"。模型的参数、知识、偏见都在采样之前就固定了。

**Q5：为什么同一句话，API 和本地部署输出不一样？**
默认参数、tokenizer 版本、推理框架的采样实现、浮点精度都可能不同。对比实验时要固定模型版本、tokenizer、参数和 seed。

## 十一、总结

把这一篇压缩成一条链：

```
输入 → 模型 → 每个位置的 logits（词表大小）
     → softmax → 概率分布
     → 温度（压尖/摊平）
     → top-k / top-p（截断长尾）
     → 重复惩罚（压制复读）
     → 采样 → 选出一个 token
     → 拼回输入，重复
```

记住四句话：

1. **模型输出的是分布，不是决定**；采样策略决定"怎么选"。
2. **温度控制冒险程度**：低温柔顺保守，高温发散随机。
3. **Top-k 是固定名额，Top-p 是动态名额**；后者更常用。
4. **采样不能提升知识，只能改变表达**；要事实准确，靠检索、工具和验证。
